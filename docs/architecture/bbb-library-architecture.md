## Target architecture (decided 2026-10-09, not yet built)

```
Android / desktop browser ── TLS 1.3, hybrid post-quantum key exchange (X25519MLKEM768) ──► Vercel (Hobby)
   service worker (Serwist): app shell, shelf, statistics JSON, opened books, presenter drafts
   Next.js: public pages server-rendered and cached (tag purged on presenter save)
            Library Room = browser app on Flow D (tap-start prefetch, adaptive tiers)
            presenter / admin = browser app behind login
   rewrite /api/* with x-origin-secret ──► DigitalOcean droplet, Bangalore (BLR1), 1 GB
        Caddy 2.10+ (TLS with X25519MLKEM768; rejects requests without the origin secret)
        ├─ FastAPI: public router (GET, ETag, CDN-Cache-Control) │ admin router (role in JWT) │ health
        ├─ Better Auth sidecar: passkeys, email links via PostHog, JWKS (Ed25519)
        ├─ book_club_archivist.db (public by intent) + auth.db (private)
        └─ nightly sqlite .backup of both, copied off the droplet (auth.db encrypted)
```

How a request flows:

1. The phone loads the page from Vercel. Public pages arrive already rendered.
2. The page calls `/api/...` on the same Vercel address. Vercel forwards it to the droplet with a secret header.
3. Caddy checks the header; FastAPI answers from SQLite. A write first checks the login token and role.
4. Public answers may be cached on Vercel's CDN; private answers never are.

## Running the application (local development)

### Backend (FastAPI)

```bash
# Install dependencies
pip install -r requirements-api.txt

# Run the server
uvicorn app.api.main:app --reload --port 8000
```

### Frontend (Next.js)

```bash
cd frontend

# Install dependencies
npm install

# Run the development server
npm run dev
```

The frontend will be available at http://localhost:3000

Or run both with `docker compose up` (development setup; production runs as described above).

## Key decisions

- **No direct database access from the frontend.** All database work goes through the API.
- **Simple REST API.** No GraphQL. The standard is PRD §11.
- **One trust boundary.** Public routes are read-only. Every create, update or delete route checks the login token and role on the server, on every request. CORS is not a security control: it only limits which browser pages may call the API.
- **Personal data apart.** Account data (email, passkeys, sessions) lives in `auth.db`, never in the public archive database.

Every decision with its date and sources: `imperative_decisions.md` §6.

## Proxy hardening checklist (launch gate, D35)

1. **Strict rewrite patterns.** `/api/:path*` goes to one fixed host; numeric IDs use `:id(\\d+)`; a destination is never built from user input (Vercel guide: loose rewrites enable open redirects and XSS).
2. **Origin lock.** Vercel adds an `x-origin-secret` header on every rewrite; Caddy rejects requests without it (timing-safe comparison). The droplet firewall allows only 80, 443 and SSH by key.
3. **No caching of private data.** Auth, admin and presenter responses send `Cache-Control: private, no-store`, and `x-vercel-enable-rewrite-caching: 0` is set on `/api/auth/*` and `/api/admin/*`. New Vercel projects cache rewrite responses by default when upstream sends cache headers.
4. **Visitor IP.** Trust `x-real-ip` and `x-forwarded-for` only on requests that carry the origin secret; rate limits use them per IP, and per account when logged in.
5. **Cookies.** `__Host-` prefix, `Secure`, `HttpOnly`, `SameSite=Lax`. CSRF: Better Auth's origin check plus an `Origin` header check on every FastAPI write.
6. **Auth in the API.** FastAPI enforces auth on every write. Next.js middleware is for user experience only (CVE-2025-29927 showed middleware-only auth can be bypassed).
7. **Headers.** HSTS; content security policy `default-src 'self'` plus the cover-image hosts (`i.gr-assets.com`, `*.mzstatic.com`, see `DOMAINS.txt`); `X-Frame-Options: DENY`; `X-Content-Type-Options: nosniff`; `Referrer-Policy: strict-origin-when-cross-origin`; `Permissions-Policy`.
8. **Body size.** Uploads are capped at 4.5 MB (4,500,000 bytes) in the API, the same as Vercel's request-body limit (D36), so every upload can pass through the proxy. Multipart headers add a few hundred bytes, so a file right at the cap may be refused by Vercel first; the admin page should check the size before sending.
9. **TLS.** Caddy 2.10+ offers X25519MLKEM768 by default; confirm in Caddy's logs that Vercel's connection negotiates it.
10. **Logs.** Never log tokens, cookies or `Authorization` headers. Vercel Hobby keeps runtime logs for 1 hour, so the droplet keeps its own logs.
11. **Firewall rules on Vercel.** Hobby allows 3 custom rules: rate-limit `/api/auth/*`, block known bad agents, and a written runbook for Attack Mode.
12. **Real-device check before launch.** Android Chrome, iOS Safari 26 and LibreWolf: login cookie works, the post-quantum key exchange shows in the browser's security panel, and no private response comes back with `x-vercel-cache: HIT`.

## Cache layers

Four layers must invalidate together when a presenter saves a meetup:

| Layer | What | Strategy | Invalidated by |
|---|---|---|---|
| Service worker | App shell, hashed JS and CSS, fonts | Cache first | New build |
| Service worker | Shelf JSON, public statistics JSON | Stale-while-revalidate | Data version bump on presenter save |
| Service worker | Book detail | Network first, cache fallback | n/a |
| Service worker | Covers | Cache first, size-capped | Oldest evicted first |
| Service worker | Auth, admin and presenter calls | Network only | Never cached |
| Vercel CDN | Public GET responses | `CDN-Cache-Control` + `Vercel-Cache-Tag` | Tag purge on presenter save |
| Browser HTTP cache | Everything | `ETag` from FastAPI | Conditional GET |
| Droplet | Precomputed statistics and timeline JSON | Rewritten on presenter save | n/a |

## Accounts and recovery (D5, D32)

- **Sign-in:** passkeys first; email and password as the alternative; email links for registration and recovery, sent through PostHog's email channel from a club mail subdomain (needs SPF, DKIM and DMARC records on the club domain).
- **Forgot password:** Better Auth's `sendResetPassword` sends a one-time link; `revokeSessionsOnPasswordReset: true` signs out every other device after a reset. Passwords are hashed with scrypt (Better Auth's default). With `requireEmailVerification`, sign-up never reveals whether an email already has an account.
- **Lost passkey:** recover through a verified-email link, then register a new passkey.
- **Post-quantum status (verified 2026-10-09):**
  - **Transport:** browser to Vercel and Vercel to Caddy use the hybrid X25519MLKEM768 key exchange (RFC 10024; Chrome 131+, Firefox 132+, Safari 26+).
  - **Passkey signatures:** classical ES256 or EdDSA (D32). IANA registered ML-DSA for COSE (−48, −49, −50; RFC 9964), and SimpleWebAuthn 14+ (under Better Auth) can verify it on Node 24.7+, but no mainstream phone creates ML-DSA passkeys yet. Revisit when phones ship it, and size the key column for keys 20 to 40 times larger.
  - **Login tokens:** Ed25519 today; plan a rotation when ML-DSA JWT support lands in the libraries.
  - `auth.db` stays private, because forging a passkey signature would need the stored public key.

## Secrets

SOPS + age: secrets are kept encrypted in the repository, one age key per admin (D7). Adding or removing an admin means re-encrypting; git history is the audit trail. Infisical was considered and deferred: its free cloud plan has no audit log, and self-hosting needs Postgres and Redis on a far larger server.

## Backups and recovery (D33)

- **Targets:** at most 24 hours of data lost (RPO), site back within 4 hours (RTO).
- **Nightly:** `sqlite3 .backup` of both databases (safe while the app runs), copied off the droplet; `auth.db` encrypted before upload. On meetup day, an extra backup runs right after every presenter save.
- **Proof:** a restore drill every quarter on a scratch machine, timed and written down. An alert fires if no backup has run in 26 hours.
- Rule from RTIH `specs/backup-dr.md`: a backup that has never been restored is a hope, not a backup.

## Founder review (2026-10-09)

**Still relevant.** All 7 listed endpoints exist in `app/api/main.py`; the API now has about 25 more (members, authors, synopsis, admin, suggest). 15 of 16 project-structure paths exist; the file used to be `ARCHITECTURE.md` (fixed above). Missing from the tree: `app/cli/`, `app/importers/`, `app/schemas/`, `app/services/`, `Dockerfile`, `docker-compose.yml`.

**Data Flow and Key Decisions: kept.** One API between the UI and the database keeps coupling low and matches PRD §7.0 (one contract, one client). Weak point for scale: `app/api/main.py` holds every route in one module, which lowers cohesion; splitting it into FastAPI routers per area is the first step when it grows.

**Planned alterations**

- **Simple REST API:** stays REST. Goals: better API security, flexibility, and tooling such as Swagger docs for the API rules. Swagger is already served by FastAPI at `/docs`. See `docs/plans/backlog.md` R4.
- **CORS:** make sure create, update and delete cannot damage the database. See backlog R5.

**Deployment (point of contention).** SQLite stays for simplicity; PostgreSQL makes more sense once statistics, RAG and MCP integration arrive. Vercel for testing and the demo showcase with full features (less weight on statistics). The goal is a website of its own. See backlog R6.
