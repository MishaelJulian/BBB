# Slice D (recovery phrase, forgot password, reset codes, session lengths): notes (2026-10-19)
Branch `slice-d` (off `slice-bc` 1d83814), worktree `BBB-vercel-demo-slice-d`. `tsc --noEmit` and `next build` clean (build run with the local DB). 35 vitest tests pass on `src/lib` against a throwaway Postgres. Nothing pushed; nothing written to the live database, storage or Vercel. Design and attacker analysis: `docs/ux/slice-d-design.md`.

## What is done
1. Recovery phrase: 12 words, each `crypto.randomInt(2048)` over the embedded BIP39 English list (132 bits; not a checksummed mnemonic), hashed with scrypt (N=32768, r=8, p=1, random salt) in our table `recovery_phrases`. Shown once on `/recovery?first=1` after sign-up or the first sign-in since phrases began, and regenerable from Account (asks the password; 5 tries per 10 min). A first phrase without password is only allowed in the first 30 minutes of a session on a login that never had one.
2. Forgot password `/forgot` (mockup flow: method tabs, email + 12 words or admin code, new password with Show/Hide, new phrase shown once, then signed in on Me). One request `POST /api/auth/forgot` does the whole check and sets the password through the Supabase Admin API (`SUPABASE_SERVICE_ROLE_KEY`, server only). Generic failure text for every wrong case; limits via `hit_rate_limit` (15/h per IP, 5/15 min and 10/day per email, counted for unknown emails too = lockout); minimum answer time 700 ms; scrypt always run; every step in `audit_log` (`auth.reset.ok/failed/blocked/error`, `auth.phrase.*`), never the words, code or password. The secret is consumed first and given back if Supabase refuses the password. All older sessions are refused afterwards (`auth_security.valid_after`, plus best-effort removal from `auth.sessions`).
3. Admin reset code: "Issue a reset code" on the Admin member page (linked accounts only), `POST /api/admin/members/[id]/reset-code` (admin only). Crockford 10 characters, hashed as sha256("reset:"+code), one use, 24 hours (wave0 line 546), shown once with Copy, older unused ones revoked. Listed in Codes ("Reset code" beside "Claim link", one list, Revoke works for both) and in All changes ("Issued a reset code", Undo = revoke).
4. Session lengths in our code: admin 24 h, member 30 d, "Keep me signed in" 90 d (checkbox on sign-in only, off by default, mockup wording), measured from sign-in. `caller()` in `src/lib/session.ts` reads `session_id` and the `amr` timestamp from the Supabase-validated JWT and our own `session_prefs` row (the earliest start wins, so a refresh cannot extend it), answers 401 `session_expired` ("Your previous session has expired. Sign in again.") and ends that Supabase session. Client: `authFetch` signs out on that answer, `useMe` checks the same arithmetic locally; `/login?expired=1` shows the notice. Keep can only be set in the first 10 minutes of a session and never for admins.
5. Screens wired: login (keep checkbox, real "Forgot your password?" link, expiry and reset notices), `/forgot`, `/recovery`, Account (Recovery phrase row and screen). 2FA: not built; the mockup's Two-factor row is left out.

## How verified
- Vitest (35 on src/lib, local DB, each test in a rolled-back transaction): word list is the BIP39 file byte for byte; phrase generation, normalising, scrypt hash/verify; reset by phrase and by code; one-time use; expired, revoked, someone else's and claim codes refused with the same message as an unknown email; a password refused by Supabase gives the secret back; lockout (5 per 15 min per email, existing or not, 15 per hour per IP); minimum time; audit rows hold no secret; session allowances 24 h / 30 d / 90 d at the exact boundary; keep ignored for admins and not addable later; a slid amr timestamp does not beat our start row; `valid_after`; `caller()` answers 401 `session_expired` and calls Supabase logout.
- Playwright 390x844 against `next dev` with a stub Supabase Auth issuing JWTs with `session_id` and `amr` (refresh keeps the amr time): sign-up shows the phrase once (reload shows none); forgot with the words (Show/Hide, new phrase, signed in); old phrase refused; repeated wrong phrases lock out; unknown email gets the same text; admin issues a code (hash only stored, appears in Codes and All changes), member uses it once, reuse and expired refused; default 30 d, keep 90 d, admin 24 h by shifting session start times (server and browser-only variants, and a refreshed token); Account recovery (wrong password refused, right one shows words). No overflow, no touch target under 44 px on our screens (the admin "Home" shell link is 42 px wide: Slice C), no console errors.
- HTTP: no token 401; member token on admin reset-code, codes, revoke 403; unlinked member 409; password tries on "new phrase" end in 429; code list never contains a code or hash.

## Open risks
- Not tested against real Supabase Auth: that `amr[].timestamp` stays at sign-in time across refresh (documented GoTrue behaviour; our own `session_prefs` row caps it anyway), that the Admin API `PUT /auth/v1/admin/users/:id` sets passwords as expected, that `auth.sessions` can be cleared by the `DATABASE_URL` role, and Supabase's own password rules (their message is shown on 422).
- Lockout can be abused to block a victim's reset for 15 minutes (anyone knowing the email). Accepted; the phrase itself cannot be guessed.
- A stolen still-valid token works until its allowance ends; there is no per-token revoke other than password reset and expiry.
- Google/Apple sign-in (if switched on) skips `/api/session/start`; the session is recorded on first server sight (30 days, no keep).
- The shown-once phrase is lost if the page is closed before saving; the member makes a new one from Account.
- Existing members get their first phrase on their next sign-in (redirect to `/recovery?first=1`); existing sessions are not forced out.
- Changing the password in Account opens a new Supabase session: its start time restarts (the keep choice is carried over).

## Defaults I took (please confirm)
Phrase from the BIP39 list with 12 independent words (132 bits); scrypt N=32768; forgot is verified in one request at the second screen (a wrong phrase shows after "Set password", then returns to the first screen); after a reset the member is signed in automatically with the new password, falling back to /login; limits 15/h IP, 5/15 min and 10/day per email; minimum 700 ms; keep only settable in the first 10 minutes; first phrase without password within 30 minutes; the Two-factor row is omitted; `auth.*` audit rows are hidden from All changes (visible in the table); Undo of "Issued a reset code" revokes it.
